# Feasibility and platform review

Reviewed 2026-10-25. This implementation is an experimental MVP, not a universal or production-validated Instagram blocker.

## Approach

Android's public [AccessibilityService](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService) provides window/content events, node trees and global Back. No supported API specifically exposes "Instagram Reels viewing". ReelsGuard therefore uses replaceable, deterministic classifiers and returns UNKNOWN when evidence is missing. No root, APK patching, private files, gestures, OCR, hidden APIs or privileged permission bypasses are used.

The current candidate adapter requires an exact clips-viewer ID, a sufficiently large viewer region and at least two distinct clickable clips actions under that viewer (exact candidate IDs or exact recognized English accessibility labels). Stories/chat/feed/profile markers conflict with viewer evidence and prevent blocking. The viewer ID is also described by the independent [Basta developer](https://basta.senaproject.online/en/accessibility-permission); that report is corroboration of the naming, not validation of this app. These identifiers are **unverified candidates**, not official Instagram contracts or tested compatibility records. The real implementation can execute Back and accounting when this evidence appears, but a current Instagram version may expose none of it and remain entirely unblocked. This is a deliberate fail-open limit, not a silently claimed success.

[TYPE_ACCESSIBILITY_OVERLAY](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#TYPE_ACCESSIBILITY_OVERLAY) allows the enabled service to create a visible touch-consuming cover without SYSTEM_ALERT_WINDOW. The cover uses a unique clickable Reels-navigation node's bounds plus exact ID/label, real app/window bounds and system insets. It appears only when blocking applies (all-block mode or exhausted quota). It does **not** remove Instagram's button. No trusted bounds means Back-only fallback. Below API 30, inset-safe covering is disabled; blocking/timing still operate. Multi-window, secondary displays and keyboards/panels fail open. Event delivery/OS scheduling cannot guarantee literally zero-frame stale overlays; each foreground event and active tick revalidates, and window-change cleanup minimizes the race.

Global Back is attempted at most once per detected viewing episode, with a cooldown and immediate foreground recheck. If Android rejects it or Instagram keeps the viewer open, ReelsGuard does not retry endlessly. Opening a shared Reel from another app can return to that app or launcher because Android controls the back stack. Public APIs cannot guarantee a previous Instagram screen exists; no kill/force-stop/home action is issued.

## Timing and lifecycle

The service is system-managed and does not depend on the activity. Monotonic elapsed time measures only confidently detected foreground Reels while protection is enabled. A one-second active-only tick is necessary for a static video to reach the allowance and checkpoint durable usage. No idle polling, wake locks or foreground service is used. Incomplete trees, app changes, screen lock, consent withdrawal and disabling pause accounting. DataStore failures are surfaced and actions pause rather than resetting the quota.

Local-midnight splitting uses `java.time` zone rules, including 23/25-hour DST days. Changes to wall time do not manufacture additional elapsed viewing time. Timezone changes carry the larger applicable total to prevent free quota by zone hopping. Public BOOT_COUNT distinguishes reboot from same-boot restart. Clock changes combined with reboot and data clearing remain outside a voluntary offline tool's guarantees. Up to about one second (plus storage scheduling latency) of current usage can be lost on abrupt process death; downtime is never counted. Force-stop does not erase saved totals but can stop protection itself.

## Versions and policies

The official [AGP 9.2 compatibility table](https://developer.android.com/build/releases/agp-9-2-0-release-notes) supports API 37.0, Gradle 9.4.1 and JDK 17 with built-in Kotlin 2.2.10. The project uses AGP 9.2.1, these compatible versions, and the stable API 37.0 SDK package. API 26 minimum provides native `java.time`; Pixel 8 is within the supported OS range. [Android 17 setup](https://developer.android.com/about/versions/17/setup-sdk) documents compile/target API 37. The current [Play target requirement](https://support.google.com/googleplay/android-developer/answer/11926878) is API 36 or newer for new mobile submissions after August 31, 2026.

[Google Play Accessibility API policy](https://support.google.com/googleplay/android-developer/answer/10964491) requires declaration and disclosure/consent for non-disability tools. ReelsGuard sets `isAccessibilityTool=false`. Its automation follows fixed user-configured rules; it does not independently plan arbitrary actions. A Play release still needs a reviewed Accessibility declaration, demo, store listing, privacy policy/Data Safety answers, developer-account compliance and approval. This project does not claim approval or promise eligibility. See [permissions policy](https://support.google.com/googleplay/android-developer/answer/9888170) and [prominent disclosure](https://support.google.com/googleplay/android-developer/answer/11150561). Sideloaded accessibility services may be subject to Android Restricted Settings; users must make that trust decision themselves.

## Verification boundary

Unit tests establish behavior for synthetic node evidence, timing, policies and restoration. APK/CI success establishes buildability. Emulator tests establish only the tested app lifecycle and UI. None establishes Instagram compatibility, Play approval, Pixel 8 physical-device behavior or OEM battery reliability. Use the manual matrix before describing any Instagram version as supported.
