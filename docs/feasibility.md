# Feasibility and platform review

Reviewed 2026-10-25. This implementation is an experimental MVP, not a universally compatible or production-certified Instagram blocker.

## Approach

Android's public [AccessibilityService](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService) provides window/content events, node trees and global Back. No supported API specifically exposes "Instagram Reels viewing". ReelsDetox therefore uses replaceable, deterministic classifiers and returns UNKNOWN when evidence is missing. No root, APK patching, private files, gestures, OCR, hidden APIs or privileged permission bypasses are used.

The current candidate adapter requires an exact clips-viewer ID, a sufficiently large viewer region and a selected exact Reels navigation tab or at least two distinct clickable clips actions under that viewer (exact candidate IDs or exact recognized Instagram accessibility labels in English, Hungarian, German, French, Spanish, Italian or Portuguese). Stories/chat/feed/profile markers conflict with viewer evidence and prevent blocking. The viewer ID is also described by the independent [Basta developer](https://basta.senaproject.online/en/accessibility-permission); that report is corroboration of the naming, not validation of this app. These identifiers remain candidate adapters, not official Instagram contracts. The shared viewer IDs and lower navigation ID were observed on a Pixel 8 / Android 17 / Instagram 452.1.0.53.64; other variants are unverified. The real implementation can execute Back and accounting when this evidence appears, but a current Instagram version may expose none of it and remain entirely unblocked. This is a deliberate fail-open limit, not a silently claimed success.

[TYPE_ACCESSIBILITY_OVERLAY](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#TYPE_ACCESSIBILITY_OVERLAY) allows the enabled service to create a visible touch-consuming cover without SYSTEM_ALERT_WINDOW. The cover uses a unique clickable Reels-navigation node's bounds plus exact ID, real app/window bounds and system insets. It appears only when blocking applies (all-block mode or exhausted quota). Existing covers update their window bounds in place to avoid remove/add flicker; invalid or foreign windows remove the cover immediately without a delayed touch target. It does **not** remove Instagram's button. No trusted bounds means Back-only fallback. Below API 30, inset-safe covering is disabled; blocking/timing still operate. Secondary displays and keyboards/focused panels fail open. Background application windows alone do not reject the verified active window. Event delivery/OS scheduling cannot guarantee literally zero-frame stale overlays; each foreground event and active tick revalidates, and window-change cleanup minimizes the race.

Global Back is attempted at most twice per detected viewing episode, with a 250 ms retry cooldown and immediate foreground recheck. A confirmed new entry clears the previous episode's cooldown. A confirmed blocked viewer is covered by an opaque, touch-consuming accessibility overlay while Back completes; the Android system navigation and other Instagram tabs remain outside that viewer guard. The second attempt tolerates a transient failure; uncertainty and rule toggles do not refill this budget. A later fresh snapshot that still confirms the viewer after the retry cooldown reports ineffective navigation. If Android rejects it or Instagram keeps the viewer open, ReelsDetox does not retry endlessly. Opening a shared Reel from another app can return to that app or launcher because Android controls the back stack. Public APIs cannot guarantee a previous Instagram screen exists; no kill/force-stop/home action is issued.

## Timing and lifecycle

The service is system-managed and does not depend on the activity. Monotonic elapsed time measures only confidently detected foreground Reels while protection is enabled and no opaque viewer guard is attached. Enforcement never awaits disk I/O: a conflated checkpoint coroutine writes cumulative counters independently. A brief 150 ms verification tick is used while blocked navigation completes, then returns to 1 Hz. A one-second active-only tick is necessary for a static video to reach the allowance and checkpoint durable usage; content events cannot bypass that interval. Viewing transitions, date/zone/boot changes and final checkpoints save promptly. A departing service publishes its final total in memory before queuing the disk write, so a same-process reconnect inherits it. No idle polling, wake locks or foreground service is used. Incomplete trees, app changes, screen lock, consent withdrawal and disabling pause accounting. Disabled/revoked protection performs no root lookups. DataStore failures are surfaced and actions pause rather than resetting the quota.

Local-midnight splitting uses `java.time` zone rules, including 23/25-hour DST days. Changes to wall time do not manufacture additional elapsed viewing time. Timezone changes carry the larger applicable total to prevent free quota by zone hopping. Public BOOT_COUNT distinguishes reboot from same-boot restart. Clock changes combined with reboot and data clearing remain outside a voluntary offline tool's guarantees. Up to about one second (plus storage scheduling latency) of current usage can be lost on abrupt process death; downtime is never counted. Force-stop does not erase saved totals but can stop protection itself.

## Versions and policies

The official [AGP 9.2 compatibility table](https://developer.android.com/build/releases/agp-9-2-0-release-notes) supports API 37.0, Gradle 9.4.1 and JDK 17 with built-in Kotlin 2.2.10. The project uses AGP 9.2.1, these compatible versions, and the stable API 37.0 SDK package. API 26 minimum provides native `java.time`; Pixel 8 is within the supported OS range. [Android 17 setup](https://developer.android.com/about/versions/17/setup-sdk) documents compile/target API 37. The current [Play target requirement](https://support.google.com/googleplay/android-developer/answer/11926878) is API 36 or newer for new mobile submissions after August 31, 2026.

[Google Play Accessibility API policy](https://support.google.com/googleplay/android-developer/answer/10964491) requires declaration and disclosure/consent for non-disability tools. ReelsDetox sets `isAccessibilityTool=false`. Its automation follows fixed user-configured rules; it does not independently plan arbitrary actions. A Play release still needs a reviewed Accessibility declaration, demo, store listing, privacy policy/Data Safety answers, developer-account compliance and approval. This project does not claim approval or promise eligibility. See [permissions policy](https://support.google.com/googleplay/android-developer/answer/9888170) and [prominent disclosure](https://support.google.com/googleplay/android-developer/answer/11150561). Sideloaded accessibility services may be subject to Android Restricted Settings; users must make that trust decision themselves.

## Verification boundary

Unit tests establish behavior for synthetic node evidence, timing, policies and restoration. APK/CI success establishes buildability. Emulator tests establish only the tested app lifecycle and UI. None establishes Instagram compatibility, Play approval, Pixel 8 physical-device behavior or OEM battery reliability. Use the manual matrix before describing any Instagram version as supported.

## Physical lower-tab verification (2026-10-26)

Pixel 8, Android 17/API 37, Instagram 452.1.0.53.64, ReelsDetox 0.1.2. Only public control identifiers, bounds and closed label classes were inspected; no post/message text or full screen dumps were retained.

The real navigation bar began at y=2337; the system gesture recognition region began at y=2316. Combining gesture insets with system-bar insets incorrectly excluded the final 21 pixels of Instagram's Reels button and rejected the whole cover. The corrected display-bound window context uses actual system bars and cutouts. Gesture recognition regions extend into ordinary app UI and Android retains gesture priority ([public API documentation](https://developer.android.com/reference/android/view/WindowInsets.Type#systemGestures())).

Observed lower-tab bounds: (216,2211)-(432,2337). The cover was verified through its exact window decision, a button-only pixel crop, and 20 consecutive taps that left Home selected. With optional button hiding disabled, 10 lower-tab entry attempts returned to Home. The user's original protection and hiding settings were restored. These are bounded smoke tests; external links, Explore, messages, Stories and long-duration stress behavior are not newly certified by them.

## Compact setup and entry settling

Setup uses one short disclosure and one affirmative action that atomically saves consent and activation before opening Android Accessibility. Returning from system settings lands on the compact dashboard. Declining leaves protection off; Privacy/About are available directly from both setup and dashboard. Existing settings are preserved on upgrade.

New Instagram foreground/window transitions trigger at most 20 extra samples 50 ms apart to catch controls exposed after an animation, even without another content event. Normal entry bursts end when detection is ready; an explicit Instagram click starts a full bounded settling burst because readiness can still describe the previous screen. A later click replaces the burst rather than adding another job. Departure, lock and cleanup cancel it. Both blocking and time-limit mode use this mechanism. It is not an endless idle poll or a promise to cover inaccessible controls before Instagram exposes them.

Seven-language closed-label matching is unit-tested as a vocabulary, not certified as full device compatibility in all seven languages. Exact navigation IDs do not require text labels. Other languages can still work by IDs, while text-dependent corroboration may be absent.

Version 0.1.3 replaces sequential view-ID searches and parent lookups with a single explicitly prefetched root (API 33+) and a bounded traversal carrying ancestry. Root/window IPC runs off the main thread. Focus, geometry and settings changes invalidate pending results; scheduling ticks do not starve in-flight reads. Disable/revoke/lock callbacks pause accounting immediately. Authorization/generation checks stop further traversal after revocation, although an already requested Android IPC cannot be undone. Only validated snapshots and a fresh matching foreground window can authorize Back or a new cover.

Earlier version 0.1.2 cold-start pixel probes observed the cover after approximately 1.44 s, 0.68 s and 0.53 s following activity start. These include screenshot/ADB overhead and are not timing measurements for the revised 0.1.3 reader or a zero-frame guarantee.

## Version 0.1.3 review and shared-Reel correction

The physical chat exposes `thread_fragment_container` and `message_list`, rather than the previous candidate `direct_thread_message_list`. Missing that positive exit left Back's two-attempt episode exhausted across repeated shared-Reel opens. The observed identifiers now classify the chat as OTHER and rearm the next entry. A mixed viewer/chat tree remains UNKNOWN.

On API 34+, the viewer guard uses [attachAccessibilityOverlayToWindow](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService#attachAccessibilityOverlayToWindow(int,%20android.view.SurfaceControl)) with a child surface in Instagram's window coordinates. System UI layers above that parent. Only an existing attached guard may remain while System UI takes focus, including when Android omits the underlying Instagram window from accessibility's list. It cannot authorize a new cover or Back action. Foreign application focus, lock, geometry changes and revocation clear the guard. API 30–33 retain the older display-overlay fallback, which clears under System UI and does not offer this shade-retention behavior.

On the same Pixel 8 / Instagram version, five independent window-event traces confirmed shared viewer opens followed by returns to the chat. Ten normal and twenty rapid taps ended on the chat; three immediate notification-shade attempts also returned there after collapse. The user then confirmed their repeated-entry method no longer left a watchable Reel. This is bounded route evidence. An unchanged viewer with rejected Back held beneath the shade was not separately forced after the fix; other devices/API 34–36 and entry routes remain unverified.

The navigation cover is now a flat rectangle. Its dark RGB(12,16,20) matched the adjacent Instagram bar on this device; the full 216×126 button crop had that one color. Light uses white. Device theme following and manual Light/Dark overrides require no screenshot capability. Instagram theme experiments may use a different palette.
